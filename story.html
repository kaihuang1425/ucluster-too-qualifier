We did three separate rounds on three machines: benchmarking in Edinburgh, performance analysis in Durham, and a prediction model at UCL. The tasks were unrelated, but one thing happened in all three: a simple check changed our first answer. We'll show one result and one check from each.

Every round, we followed the same five steps

• Before the results, here is how we approached every round.
• Get access. Log in, check the hardware and modules, and run a small test job.
• Understand the problem. Read up on HPL, rooflines or decision trees, and run a baseline.
• Vary one parameter per experiment, with all others held constant.
• Submit each sweep as a batch of jobs, monitor them with squeue and keep every raw result.
• Every plot comes from a script, and we write up our interpretation last.
• Round 3 was a modelling task rather than a benchmark, so the sweep became a fair comparison of models on the same data split.
Round 1 Edinburgh

HPL: three settings each added 15–24%, compiler flags under 2%

A bigger problem also lifted efficiency, from 4.18 to 7.84 GFLOPS per watt.

HPL GFLOPS on one node, one parameter per sweep with the rest held fixed. Data from our submitted EPCC report (jobs 563364 and 563656).
• HPL solves one dense system Ax = b by LU factorisation. We changed one parameter at a time on one node, starting from N = 50,000.
• N, problem size. The matrix is N × N, so it takes 8N² bytes and memory sets the upper limit. Work grows as about ⅔N³ while setup, panel factorisation and communication grow as N², so a bigger N amortises that fixed overhead. 50,000 → 250,000 added 22% to GFLOPS.
• Why small N is slow. The term is N-half, the problem size at which a system reaches half its peak speed. Above it, speed climbs more slowly towards the peak, which is the flattening we see past 150,000.
• NB, block size. HPL cuts the matrix into NB × NB blocks, deals them out to the MPI ranks and feeds them to DGEMM. Bigger blocks reuse more data from cache and send fewer messages, but blocks that are too big leave some ranks idle near the end. 128 → 320 added 24%, and 384 was slower again.
• P × Q, ranks and threads. The MPI ranks form a P × Q grid and each rank owns a share of the blocks. OpenMP threads split each rank’s DGEMM. 72 × 4 was fastest at +15% over 288 × 1, and 32 × 9 was most efficient at 8.94 GFLOPS per watt.
• Compiler flags. They only change HPL’s own code. The time is spent in Cray LibSci’s precompiled DGEMM, so flags moved the result by under 2%.
• GFLOPS is ⅔N³ divided by solve time. GFLOPS per watt is that solve work divided by the whole job’s Slurm energy, so setup energy counts too. That is why raising N lifted GFLOPS per watt from 4.18 to 7.84.

HPL strong scaling, N = 100,000, NB 128, 256 MPI ranks over 1 to 4 Cirrus nodes. Efficiency = solve work ÷ whole-job Slurm energy. Data from our submitted EPCC report, HPL node sweep.
• Set-up. Same N = 100,000 and the same 256 MPI ranks, spread over one to four nodes. This is strong scaling.
• Speed. Four nodes finished 2.15 times faster, which is 54% parallel efficiency against an ideal of four times.
• Efficiency. GFLOPS per watt fell from 7.34 on one node to 4.98 on two, 4.51 on three and 4.47 on four, 39% lower overall.
• Energy. Power rose 3.2 times while job time fell only 1.9 times, so energy to solution rose 64%.
• Why. Each extra node draws power for memory, networking and cooling even when its cores are idle, and with 64 ranks per node most of its 288 cores were idle. MPI traffic between nodes also takes time away from computation.
• Takeaway. For an efficiency score, one node with a large N was the better choice.
• The check. Our first formula divided the solve’s work by the whole job’s average power, which flattered short runs. We switched to whole-job energy before comparing runs.

HPCG is limited by memory, not by cores. The extra cores only cost power, so leaving them idle gave 8% better efficiency.

HPCG, 30-minute VALID runs, 288 × 1 vs 144 × 2 ranks (jobs 570229, 571314): +8% GFLOPS per watt. Data from hpcg/results/SUMMARY.md.
HPCG is the opposite kind of benchmark: it mostly reads data from memory. When we ran it on half the cores, it went just as fast and used 7% less power. If removing half the workers doesn't slow you down, the workers aren't the bottleneck. Memory is. So our most efficient HPCG run left half the node idle: 8% better efficiency.

Both nodes met their compute spec, but memory bandwidth reached only 56% and 71% of spec

DINE2 has twice the cores of DINE but only 1.7 times the bandwidth, so each core gets less memory: 6.2 against 7.2 GB/s.

Medians of 3 runs of peakflops_sp (AVX or AVX-512 FMA) and triad_mem (non-temporal stores). Compute spec is sockets × cores × base GHz × FLOP per cycle. Memory spec assumes the rated DIMM speed, which we could not verify. Data from analysis/overnight-20261022T224854Z/ceilings.csv and report/report.tex.
• How we found each limit. We ran each likwid-bench kernel at several thread counts and placements, three times each. The limit is the highest full-node median, not the single fastest run, so one lucky run cannot inflate it.
• Compute limit, peakflops_sp. It runs fused multiply-adds on the widest vectors, AVX2 on DINE and AVX-512 on DINE2, using data that stays in registers and L1 cache. Memory is never involved, so the only thing it can hit is how fast the cores calculate.
• Memory limit, triad_mem. It computes a = b + c × d over 2 GB, far more than any cache, so every byte comes from main memory. It does only 2 FLOPs per 24 bytes or so, so the cores are never the bottleneck. Its non-temporal stores write straight to memory and skip the extra read a normal store causes.
• Why triad and not read-only. Triad reads and writes, like real codes do. A read-only kernel reached 439.5 GB/s on DINE2, so this limit depends on the access pattern.
• Against the vendor spec. Compute came out 8 to 9% above the base-clock spec, which we attribute to turbo. Bandwidth reached 56% of the DIMM-rated bound on DINE and 71% on DINE2. That bound is never reached in practice, and we could not verify the DIMM speeds.
• Ridge point. Compute limit divided by memory limit. Any code below about 15 FLOPs per byte on DINE, or 23 on DINE2, is limited by memory.

Grid, a physics code, is limited by memory, not by compute

~2FLOPs per byte fetched from memory. The nodes need 15 to 23 to keep their cores busy.
61–71%of the memory-bandwidth limit reached, so Grid uses memory well.
Computeisn't the limit. Moving data is.
Grid on DINE and DINE2. Ceilings from likwid-bench (FP32 peak, triad); Grid intensity 1.57 and 2.08 FLOP/byte from likwid-perfctr, whole process. Data from ceilings.csv and report/report.tex.
• The axes. Across is FLOPs per byte, how many calculations a code does for each byte it fetches from memory. Up is speed in GFLOP/s. Both axes are log scale.
• Compute limit. likwid-bench peakflops_sp runs only fused multiply-adds on data held in registers, so memory is never involved. It reached 3,341 GFLOP/s on DINE and 9,287 on DINE2.
• Memory limit. likwid-bench triad_mem streams 2 GB through main memory with almost no maths, so only memory can slow it down. It reached 231 GB/s on DINE and 398 on DINE2.
• Flat line. No code can run faster than the compute limit, whatever its FLOPs per byte.
• Sloped line. A code doing x FLOPs per byte can run no faster than bandwidth × x, so the memory limit is a line that rises with x.
• The roof. A code’s best possible speed is the lower of the two lines at its FLOPs per byte. They meet at the ridge point, compute divided by bandwidth, about 15 on DINE and 23 on DINE2.
• Reading it. A code under the sloped line is memory-bound, so faster cores would not help. A code under the flat line is compute-bound. FLOPs per byte is fixed by the code, so we do not move along the axis. We only read off where Grid sits.
• Grid. We ran Grid inside likwid-perfctr, which counted its FLOPs and memory bytes in the same run. It does 1.57 FLOPs per byte on DINE and 2.08 on DINE2, far left of both ridge points.
• Conclusion. Grid sits under the sloped line on both nodes, so memory bandwidth limits it, not compute. On DINE, memory allows about 363 GFLOP/s at 1.57 FLOPs per byte, against a compute limit of 3,341. Grid uses 61 to 71% of the measured bandwidth.

• Each week we changed how we worked, based on what went wrong the week before.
• Week 1, Edinburgh. We learned the machine from our own results and swept layouts without a hypothesis. So from week 2 we ran a recon job first, chose layouts from the topology, used one parameterised script with job arrays, and had every job write its own results row.
• Week 2, Durham. That paid off: 205 jobs by Friday morning, each recording its git hash, modules, build flags and host, and 95 of 97 overnight runs succeeded. The Clang-versus-GCC gap turned out to be thread placement, which gave us a rule for week 3: before blaming one factor, check what else differed between the runs.
• Week 3, UCL. The data file arrived readable by every user, so we locked it down before any analysis. Then we applied the week 2 rule: we checked what our score ignored, and tested every factor against shuffled copies and random noise. Only age survived.
• That's the habit we'd take to the finals: check before you believe. Thank you.

Limitations of these results

EPCC Cirrus

We did not isolate which components drew the extra power on multiple nodes.

GFLOPS per watt includes setup energy before the timed solve, so all efficiency figures are conservative.

DiRAC DINE

Counter-based intensity averages over the whole process and cannot be assigned to one Grid kernel.

DIMM speeds were not verified, so the memory specification is an upper bound.

UCL Condenser

The test set holds 60 resistant patients, so model differences below one standard deviation are not meaningful.

The data under-represents White patients and covers only ages 20 to 79, so the model may not generalise.

Each round has limits we want to state plainly. On Cirrus, we saw extra power on multiple nodes but did not measure which components drew it. On DINE, our intensity numbers come from whole-process counters, and the memory specification assumes DIMM speeds we could not check. For the UCL model, the test set is small and the data is not representative, so the model should not be read as a clinical result.

Conclusions

01

HPL efficiency on Cirrus is set mainly by problem size per node. Four nodes ran 2.15 times faster but used 64% more energy than one.

02

Grid is bandwidth-bound on both DiRAC nodes, at 61–71% of the memory roof. Thread placement mattered more than the choice of compiler.

03

Age is the only factor in the UCL dataset that beats a permutation null. A readable depth-3 tree performs within noise of a random forest.
