UCLuster Too

Performance analysis on EPCC Cirrus and DiRAC DINE, and model selection on UCL Condenser.

Ada Ge · Bobby Ta · Eric Huang · James LokeNovember 2026
We are UCLuster Too. This talk covers the three qualifier sub-challenges in the order we did them. Each round left an open question that shaped how we approached the next one, so we present the results together with the reasoning that linked them.

This is the outline. Round 1 ended with a hypothesis about memory bandwidth that we could not test on Cirrus. The Durham brief asked us to measure exactly that. Durham also showed us how easily a confound can look like a real effect. That is why we built permutation controls into the UCL analysis from the start.

Brief summarised in notes/epcc-week1-rundown.md (UCL repository). Energy from Slurm ConsumedEnergyRaw. Every job ran with --exclusive.
Each Cirrus node has two 144-core AMD EPYC 9825 processors. The cores are grouped into 24 chiplets of 12 cores, and Slurm exposes 8 NUMA domains. Half of the marks were for GFLOPS per watt. Every run therefore recorded energy from Slurm’s counters as well as GFLOPS.

On one node, problem size, block size and layout each added 15 to 24% to HPL speed, and compiler flags under 2%

Problem size N50,000 → 250,000 · NB 128 · 16 × 16 ranks+22%
Block size NB128 → 320 at N = 100,000+24%
MPI ranks × OpenMP threads288 × 1 → 72 × 4 · 32 × 9 most efficient+15%
Compiler flagsCray -O2, -O3, -Ofast, -flto≤2%

HPL work grows as N³ while setup and communication grow as N². Raising N also lifted GFLOPS per watt from 4.18 to 7.84. Most of the runtime is DGEMM inside Cray LibSci, which compiler flags do not change.

HPL GFLOPS on one node, changing one parameter per sweep with the rest held fixed. Data from our submitted EPCC report, HPL sweeps of N, NB, MPI × OpenMP layout and compiler flags (jobs 563364 and 563656).
We changed one HPL parameter at a time on one node, starting with problem size at N = 50,000. Going up to 250,000 added 22% to GFLOPS. A small run spends a large share of its time on overhead. Setup, panel factorisation and communication grow as N², but the useful matrix multiply grows as N³, so a larger N amortises that fixed cost. HPL describes this with N-half, the problem size at which a system reaches half its peak speed. Above it, speed climbs more slowly towards the peak, which is the flattening we see past 150,000. GFLOPS per watt rose even more, from 4.18 to 7.84, because Slurm also counts the setup energy. Block size added 24%, from NB 128 to 320. For the layout, 72 ranks of 4 threads was fastest and 32 ranks of 9 threads was most efficient, both ahead of 288 single-threaded ranks. Compiler flags moved the result by under 2%, because the time is spent in the vendor’s DGEMM library.

Parallel efficiency was 54%. Power rose 3.2 times while job time fell only 1.9 times, so energy to solution rose. Extra nodes draw power for memory, network and cooling even when their cores are idle.

Strong scaling with N = 100,000, NB 128 and the same 16 × 16 grid of 256 MPI ranks spread over 1 to 4 nodes. GFLOPS per watt is solve work divided by whole-job Slurm energy, and average power is that energy over elapsed time. Data from our submitted EPCC report, HPL node sweep.
We kept the problem fixed at N = 100,000 with the same 256 MPI ranks, and spread them over one to four nodes. Four nodes finished 2.15 times faster, which is 54% parallel efficiency, but used 64% more energy. GFLOPS per watt fell from 7.34 on one node to 4.98 on two, 4.51 on three and 4.47 on four. Two things cost energy. Each extra node draws power for memory, networking and cooling whether or not its cores are busy, and with 64 ranks per node most of its 288 cores sat idle. MPI traffic between nodes also takes time away from computation. So for an efficiency score, one node with a large N was the better choice.

On one node, HPCG delivered under 1% of HPL’s GFLOPS at a similar power draw

HPL · dense solve15,345GFLOPS at 1,154 W average
HPCG · sparse solve134.5GFLOPS at 977 W average

HPL spends its time in dense matrix multiply, which reuses each operand many times from cache. HPCG spends its time in sparse matrix-vector products and a Gauss-Seidel smoother, which use most values once before moving on.

HPL job 571593 (N = 250,000). HPCG job 571314 (30-minute VALID run, 144 ranks × 2 cores). The GFLOPS ratio is 114 and the GFLOPS per watt ratio is 93. Data from hpl/results/SUMMARY.md and hpcg/results/SUMMARY.md.
Both benchmarks ran on the same node type at a similar power draw. HPCG delivered 114 times fewer GFLOPS. The two codes do very different work per byte loaded. Dense matrix multiply reuses data from cache. Sparse kernels read each value and move on. Our expectation was that HPCG is limited by memory, and the next slide is how we tested that on Cirrus.

If throughput holds with half the cores idle, the cores are not the limiting resource. This is consistent with memory bandwidth saturating before all 288 cores are busy. Cirrus gave us no way to measure bandwidth, so this became our hypothesis for round 2.

30-minute VALID finals on the same binary and global problem. Job 570229 (288 × 1) against job 571314 (144 × 2) gives +8.1% GFLOPS per watt. Pure MPI ran 1.95 times faster than 24 MPI × 12 OpenMP because the reference smoother is not threaded. Data from hpcg/results/SUMMARY.md, sections B, F and G.
We ran HPCG with 144 ranks, each given two cores but only one thread, so half the cores sat idle. Throughput rose slightly and power fell by about 7%, which gave 8% more GFLOPS per watt over a full 30-minute valid run. If removing half the workers does not slow the work, the workers were not the bottleneck. Memory bandwidth is the obvious candidate, but we had no direct measurement of it on Cirrus. That is the question we carried into Durham.

The Durham brief asked how close each node gets to its vendor specification, and where the Grid lattice QCD benchmark sits between the compute and bandwidth limits. That was the measurement we had been missing on Cirrus. The two nodes differ in vendor and in core count, which made the comparison useful.

Both nodes met their compute specification, but measured bandwidth reached only 56% and 71% of the memory specification

The ratio of the two measured ceilings is the ridge point. Below about 14.5 FLOPs per byte on DINE and 23.3 on DINE2, memory sets the speed.

Medians of 3 runs of peakflops_sp (AVX or AVX-512 FMA) and triad_mem (non-temporal stores). Compute spec is sockets × cores × base GHz × FLOP per cycle. LIKWID’s peak FLOP kernel slightly exceeded the base-clock specification on both nodes, which we attribute to turbo. Measured memory bandwidth reached 56% of the specification on DINE and 71% on DINE2. Dividing the two measured ceilings gives the ridge point. Any code below about 15 FLOPs per byte on DINE, or 23 on DINE2, is limited by memory.

DINE · DINE2. Points use likwid-perfctr FLOPS_SP and MEM at full node (32 and 64 threads) and average over the whole process, not a single kernel. The best Grid kernel runs reached 361 and 864 GFLOP/s, about 11% and 9% of the FP32 ceiling. Data from docs/slides-D.md, docs/submission-review.md and ceilings.csv.
Hardware counters on full-node Grid runs put its intensity at 1.6 and 2.1 FLOPs per byte. That is an order of magnitude left of both ridge points, so Grid is bandwidth-bound on both nodes. At that intensity the bandwidth roof allows about 363 GFLOP/s on DINE and 826 on DINE2. Grid achieves 71% and 61% of those values. Its own memory benchmark reaches 98% and 89% of LIKWID’s triad, so the streaming itself is efficient. The caveat is that the counters cover the whole process, including setup, rather than one kernel.

An apparent compiler effect on DINE2 was caused by thread placement

✕Default OMP_PROC_BIND=close

✓Socket-ordered OMP_PLACES={0}:32:2,{1}:32:2

DINE2 numbers socket 0 cores even and socket 1 cores odd. With close binding, consecutive threads alternate between sockets. Threads that share lattice data then sit on different sockets.

+58%

from socket-ordered places at L = 24. Clang’s apparent advantage was the same effect, produced by LLVM’s OpenMP runtime. An apparently fast node, gc007, had the same explanation.

Placement drawn for threads 0 to 7 only. Numbers in cells are OS core IDs. Best case after the fix was 361 GFLOP/s on DINE (GCC, 32 threads, L = 48) and 864 GFLOP/s on DINE2 (GCC, 128 SMT threads, socket-ordered, L = 24). Data from report/report.tex, docs/slides-A.md and analysis/data/tuning_summary.csv.
Early tuning data suggested that Clang beat GCC on DINE2, and that one node, gc007, was unusually fast. Both turned out to be thread placement. DINE2 numbers its cores even on one socket and odd on the other, so the default close binding splits neighbouring threads across sockets. Socket-ordered places gave up to 58% at L equals 24. Clang looked faster only because its OpenMP runtime happened to place threads differently.

The trend is consistent with threads sharing memory bandwidth, but the curves alone cannot isolate the cause. In weak scaling (L24 on 2 threads to L48 on 32) DINE kept 56% of per-thread throughput and DINE2 kept 32%. Data from analysis/overnight-20261022T224854Z/SUMMARY.md.
Both nodes keep getting faster with more threads, but well below the ideal line. DINE reaches 17 times on 32 threads and DINE2 reaches 21 times on 64. DINE2 has twice the cores of DINE but only 1.7 times the bandwidth, so each core has less bandwidth available. That matches the lower efficiency, and it is what a bandwidth-bound code should show. We say consistent with rather than caused by, because a scaling curve alone cannot separate bandwidth from synchronisation or placement effects.

The UCL brief asked which tree model best identifies patients at risk of co-amoxiclav resistance, and what the main risk factors are. The data is synthetic. It is also not representative. It contains only adults aged 20 to 79, and White patients make up 17.6% of records against about 82% of the population. Any model trained on it may not generalise to the real population.

With 24.1% of patients resistant, the unweighted tree never predicted a resistance probability above 0.5. We added class weights and ranked models by cross-validated balanced accuracy. As with our first energy formula, the original metric did not measure what the task required.

Synthetic data  Held-out test set of 250 patients, 60 of them resistant. Balanced accuracy from 5-fold cross-validation on the training set. Data from outputs/model_comparison.csv and video/teamwork-log.md (25 Oct).
Our first draft ranked trees by ROC AUC. The chosen tree never predicted a resistance probability above one half, because only a quarter of patients are resistant. It was 76% accurate and flagged nobody. ROC AUC ignores the decision threshold, so it could not catch this. We switched to class weights and balanced accuracy, which weights both classes equally. This is the same kind of error as our first GFLOPS per watt formula in round 1.

To identify risk factors we scored each column on its own and compared it with 100 shuffled copies of itself. Shuffling keeps the column’s values but breaks any link with resistance, so the shuffled scores show what chance alone produces. We also added a column of random numbers. Only age beat its null, with an AUC of 0.71 against 0.54. Our first evidence for deprivation was a forest importance of 0.09. In the noise check, a column of random numbers scored 0.16 on the same measure, because impurity importance favours columns with many distinct values.

The mistakes had a common structure. In each case the first measurement reflected a property of our method rather than of the system under study.

Across all three rounds the same thing happened. Our first reading came from the measurement method rather than from the system. The energy formula favoured short runs. The OpenMP runtime decided where threads went. Impurity importance favoured many-valued columns. In each case a control experiment exposed it. That is the main methodological lesson we take from the qualifier.

Limitations of these results

EPCC Cirrus

We did not isolate which components drew the extra power on multiple nodes.

GFLOPS per watt includes setup energy before the timed solve, so all efficiency figures are conservative.

DiRAC DINE

Counter-based intensity averages over the whole process and cannot be assigned to one Grid kernel.

DIMM speeds were not verified, so the memory specification is an upper bound.

UCL Condenser

The test set holds 60 resistant patients, so model differences below one standard deviation are not meaningful.

The data under-represents White patients and covers only ages 20 to 79, so the model may not generalise.

Each round has limits we want to state plainly. On Cirrus, we saw extra power on multiple nodes but did not measure which components drew it. On DINE, our intensity numbers come from whole-process counters, and the memory specification assumes DIMM speeds we could not check. For the UCL model, the test set is small and the data is not representative, so the model should not be read as a clinical result.

Conclusions

01

HPL efficiency on Cirrus is set mainly by problem size per node. Four nodes ran 2.15 times faster but used 64% more energy than one.

02

Grid is bandwidth-bound on both DiRAC nodes, at 61–71% of the memory roof. Thread placement mattered more than the choice of compiler.

03

Age is the only factor in the UCL dataset that beats a permutation null. A readable depth-3 tree performs within noise of a random forest.
