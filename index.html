One parameter changed per sweep, with the rest held fixed. Data from our submitted EPCC report, HPL sweeps of N, NB, MPI × OpenMP layout and compiler flags (jobs 563364 and 563656).
1. Each sweep held everything else constant and changed one variable.
2. Problem size N, 50,000 to 250,000, plus 22%.
3. Block size NB, 128 to 320, plus 24%.
4. Fewer MPI ranks with more OpenMP threads each, plus 15%.
5. Compiler flags, under 2%.• HPL solves one dense system Ax = b by LU factorisation. We changed one parameter at a time on one node, starting from N = 50,000.
• N, problem size. The matrix is N × N, so it takes 8N² bytes and memory sets the upper limit. Work grows as about ⅔N³ while setup, panel factorisation and communication grow as N², so a bigger N amortises that fixed overhead. 50,000 → 250,000 added 22% to GFLOPS.
• Why small N is slow. The term is N-half, the problem size at which a system reaches half its peak speed. Above it, speed climbs more slowly towards the peak, which is the flattening we see past 150,000.
• NB, block size. HPL cuts the matrix into NB × NB blocks, deals them out to the MPI ranks and feeds them to DGEMM. Bigger blocks reuse more data from cache and send fewer messages, but blocks that are too big leave some ranks idle near the end. 128 → 320 added 24%, and 384 was slower again.
• P × Q, ranks and threads. The MPI ranks form a P × Q grid and each rank owns a share of the blocks. OpenMP threads split each rank’s DGEMM. 72 × 4 was fastest at +15% over 288 × 1, and 32 × 9 was most efficient at 8.94 GFLOPS per watt.
• Compiler flags. They only change HPL’s own code. The time is spent in Cray LibSci’s precompiled DGEMM, so flags moved the result by under 2%.
• GFLOPS is ⅔N³ divided by solve time. GFLOPS per watt is that solve work divided by the whole job’s Slurm energy, so setup energy counts too. That is why raising N lifted GFLOPS per watt from 4.18 to 7.84.

• Speed. Four nodes finished 2.15 times faster, which is 54% parallel efficiency against an ideal of four times.
• Efficiency. GFLOPS per watt fell from 7.34 on one node to 4.98 on two, 4.51 on three and 4.47 on four, 39% lower overall.

• Takeaway. For an efficiency score, one node with a large N was the better choice.

2. So compute grew 2.78 times, but bandwidth only 1.72, since both have eight memory channels per socket. A code now needs 23 FLOPs per byte, not 15, before compute limits it. Below that it is memory-bound.
3. For compute we used likwid-bench peakflops_sp, and for memory, triad_mem.DINE has 32 AMD EPYC 7302 cores with AVX2. DINE2 has 64 Intel Xeon Gold 6430 cores with AVX-512. Compute grew 2.78 times because DINE2 has twice the cores and vectors twice as wide, at a lower clock, 2.1 against 3.0 GHz, which gives about 2 × 2 × 0.7. Bandwidth grew only 1.72 times because both nodes have eight memory channels per socket, and DINE2’s faster DDR5 adds nothing like twice the cores’ worth. peakflops_sp runs fused multiply-adds on data held in registers and L1 cache, so memory is never involved. triad_mem computes a = b + c × d over 2 GB, far more than any cache, so every byte comes from main memory. Each limit is the highest full-node median over several thread counts and placements, so one lucky run cannot inflate it. Kernel type. We ran peakflops scalar, SSE, AVX, AVX FMA and AVX-512 FMA, in single and double precision. Scalar double precision on DINE reached 274.4 GFLOP/s, 16.4% of the vector FMA peak, and AVX-512 FMA ran 1.82 times faster than AVX2 FMA on DINE2. So the compute limit only applies to code that uses wide vectors and FMA, which is why each Grid build targeted znver2 or sapphirerapids. Thread count. DINE held about 105 GFLOP/s per core at every count. DINE2 fell from about 210 per core on up to 8 cores to 146 on 32, which fits the clock dropping to stay within power limits under AVX-512. Access pattern. In GB/s on DINE and DINE2, read-only load gave 219.8 and 439.5, non-temporal triad 231.0 and 397.9, normal triad 180.5 and 393.2, and copy 156.4 and 321.9. Non-temporal stores gave DINE 28% more than normal triad because they skip the extra read a normal store causes, but made almost no difference on DINE2. Grid’s own streaming kernel reached 173.6 and 350.1 GB/s, close to normal triad, so Grid’s simple kernels do reach the memory limit. Placement. On DINE2, 32 threads spread over both sockets gave 365.5 GB/s against 195.4 with one socket filled first, so one socket saturates at about 16 cores and 182 GB/s. So thread placement matters on DINE2. Working-set size. On one core, bandwidth stepped down at each cache level. From L3, DINE reached 83.6 GB/s against 31.4 on DINE2, because DINE has small L3 slices close to each core while DINE2 spreads its L3 across the socket. This is why small Grid lattices that fit in cache ran much faster, 848 GFLOP/s at L = 16 on DINE and about 2,700 at L = 12 on DINE2.

Conclusions

01

Raising the HPL problem size nearly doubled GFLOPS per watt on one Cirrus node. Four nodes ran 2.15 times faster but used 64% more energy than one.

02

Grid is bandwidth-bound on both DiRAC nodes, at 61 to 71% of the memory roof. On DINE2, thread placement explained an apparent compiler effect.

03

Only age passed both shuffle tests on the synthetic data. Our depth-3 tree flagged 39 of 60 resistant test cases.

We worked through each round in the same five steps

01

Get access. Log in, check the hardware and modules, and run a small test job.

02

Understand the problem. Read about HPL, rooflines or decision trees, and run a baseline.

03

Vary one parameter per experiment. Sweep a single parameter with all others held constant to find its best value in the range tested.

04

Run systematic job campaigns. Submit each sweep as a batch of jobs, monitor them with squeue and retain every raw result.

05

Plot and interpret. Draw every figure from the raw data with a script, then write up what it shows.

Rounds 1 and 2 were benchmark sweeps. Round 3 was a modelling problem, so step 3 meant comparing models and settings on the same data split.

Limitations of these results

EPCC Cirrus

We did not isolate which components drew the extra power on multiple nodes.

GFLOPS per watt includes setup energy before the timed solve, so all efficiency figures are conservative.

DiRAC DINE

Counter-based intensity averages over the whole process and cannot be assigned to one Grid kernel.

UCL Condenser

The test set holds only 60 resistant patients, and the competitive models differ by less than one fold-to-fold standard deviation, so we cannot claim that one model is better.

White patients are 17.6% of records against 81.7% in the census, and ages run only from 20 to 79, so the model may not generalise.

Each round has limits we want to state plainly. On Cirrus, we saw extra power on multiple nodes but did not measure which components drew it. On DINE, our intensity numbers come from whole-process counters, and the bandwidth we compare depends on the access pattern, so the ratio is for triad. For the UCL model, the test set is small and the data is not representative, so the model should not be read as a clinical result.
